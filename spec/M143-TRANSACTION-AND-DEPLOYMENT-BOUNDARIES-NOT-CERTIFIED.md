## Proposed wire and transaction contract

The frontend sends a single `wm_import_board_wizard_atomic` RPC with the reviewed board version and contract `m143-v1`, group selection, explicit per-source-column mapping, proposed columns, matching policy and all source rows. The backend must recompute matches and validate all cells within the transaction; client preview and match IDs are not authorization.

- **Add as new:** create all rows, even when Item names match existing ones. New UUIDs are generated by the server. Existing legacy M103 import semantics are unchanged.
- **Skip:** select a mapped matching column; existing matches are skipped, unmatched rows are created. Duplicate source keys and multiple target matches abort atomically.
- **Update:** select a mapped matching column; unique matches update using `expected_item_updated_at` compare-and-swap; unmatched rows are skipped. Blank cells preserve current values. New groups cannot be used for updates.
- **New groups/columns:** created inside the same transaction. User must retain active Board edit permission. New columns require name 1–80 characters, supported type and available capacity (maximum 30 total). New status/dropdown columns currently fail closed until the UI implements explicit option approval.
- **Write integrity:** one RPC, locks and Board version comparison, no item-by-item fallback, authenticated actor, role authorization via `public.work_board_access`, native `work_board_validate_column_value` via `wm_set_board_cell`, audit event, single PostgreSQL transaction rollback on exception.
- **Security:** no secret key, no new browser-auth flow, no table grants, no change to M103's existing RPC. The new function starts REVOKE ALL, then grants EXECUTE to authenticated. It uses SECURITY DEFINER and explicitly checks Board access, activity, workspace/profiles through existing `work_board_access`.

## Functional limitations requiring later work

- Actual SQL migration DDL is in `supabase/m143/board_import_wizard_atomic_DRAFT.sql`, deliberately OUTSIDE `supabase/migrations`. It must be generated through the Supabase CLI, reviewed, and tested against a **disposable/staging** database before any production deployment. Do not paste/run in the production SQL editor.
- New status and dropdown columns require a review UI to explicitly approve labels/options; currently blocked. Existing configured status/dropdown columns are supported subject to Board schema acceptance.
- Full Monday.com subitem hierarchy is not restored; a Subitems source column remains a normal data column.
- Excel serial dates, formulas, imported relationships/attachments, large files beyond 5,000 rows, and provider-specific data semantics need dedicated fixtures and acceptance evidence.
- `config/backend-capability-manifest.ts` is **not changed** until the new RPC is deployed, so the existing Boards module's required capabilities are not broken on production.
- Live authenticated role-based tests (owner/editor/viewer, out-of-workspace, revoked identity), concurrent stale-version updates, intentional row errors/rollback, duplicate key matches, schema limit, complete E2E and check that NO partial group/column/item writes remain after rejection are required before enabling production rollout.
- The visible wizard may attempt the new RPC in the local review candidate, but without the migration the server must reject it. Do not deploy this candidate as working production functionality until the M143 database gate passes.
